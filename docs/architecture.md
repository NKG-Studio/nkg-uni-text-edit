# 架构与性能契约

## “无限大文件”的工程定义

这里的“无限大”不是突破操作系统上限，而是：

1. 所有文件大小和偏移使用 `u64`；
2. 打开、阅读和跳转的常驻内存不与文件大小线性相关；
3. 文件内容不整体进入 Rust 堆、WebView、Rope 或 DOM；
4. 全文件操作必须流式执行、可报告进度、可取消；
5. UI 不能因为底层分块而呈现成分页文档；
6. 高亮、结构、临时输出、搜索会话和单次 UI 数据量均有显式上限；
7. 搜索结果使用磁盘分页索引，达到显式配额时停止并报告，不允许耗尽临时盘。

## 分层

```text
原生桌面 UI（egui / eframe）
        │ 仅传递窗口、命中和进度
        ▼
nkg-text-engine
  ├─ FileSource        位置读取与文件快照
  ├─ TextDocument      有界窗口与行边界
  ├─ SparseLineIndex   渐进式稀疏行索引
  ├─ Search            流式、取消、磁盘结果索引
  ├─ BlockDiff         常量缓冲区、有界区段概览
  └─ WindowDiff        有界可见窗口精确对比
        │
        ▼
本地文件系统
```

核心 crate 不依赖任何 UI 框架。桌面层不得绕过核心直接整体读取文件。

## 内存上界

- 默认视口读取：`256 KiB`，硬上限 `8 MiB`；
- 默认搜索块：`1 MiB`，硬上限 `16 MiB`；模式大于块配置时自动提升有效块大小；
- 搜索模式：硬上限 `1 MiB`；
- 搜索结果：每条磁盘记录固定 `8 bytes`，UI 单次最多读取 `10,000` 条；
- 桌面搜索：每个文档最多保留 `8` 个会话，单会话磁盘索引上限 `512 MiB`；
- 当前可见区高亮：默认最多 `10,000` 个 span；
- 块对比：默认块 `256 KiB`，左右各一个固定大小缓冲区；
- 块对比概览：默认最多 `50,000` 个候选区段，超大文件自动放大概览粒度；
- 可见窗口精确对比：默认最多 `4,000,000` 个 LCS 单元格（约 `16 MiB`）；
- 稀疏索引：每 `65,536` 行或 `8 MiB`（先到者）记录一个检查点。

除稀疏索引和显式受限的结果集合外，内存不随文件大小增长。

## 行索引策略

打开文件不扫描全盘，因此刚打开时总行数未知。索引线程从头顺序扫描并逐步发布进度。
在尚未索引到的区域，界面显示字节位置和百分比；索引到达后再提供精确行号。

检查点同时受行跨度和字节跨度约束：

- 短行密集文件不会为每行分配内存；
- 普通日志从最近检查点恢复行号时通常只需扫描数 MiB；
- 单行自身超过扫描预算时允许暂时不显示精确行号，不能因此阻塞界面。

## 搜索策略

第一阶段支持字节字面量和 ASCII 不区分大小写搜索。搜索跨块保留
`pattern_length - 1` 字节重叠区，保证不会漏掉跨块命中。命中通过绝对字节范围表示。

桌面搜索不设置 `10,000` 条之类的隐式命中数截断：每个命中只把起始 `u64` 写入临时磁盘
文件，模式长度在结果表中保存一次，
搜索过程中即可读取已经提交的结果。底部结果列表只读取和渲染当前可见区域，文本上下文
再从原文件按需获取并缓存；点击结果后由连续视图定位和高亮。单会话达到 512 MiB 配额时
主动取消并明确提示，不能伪装成“已列出全部”。

每次桌面搜索创建独立的磁盘结果索引和可折叠结果组；开始下一次搜索不会覆盖既有结果。
最多保留 8 组，超过时释放最旧会话；用户删除单组或清空结果后，对应临时索引随会话释放。

高密度命中每累计 `4,096` 条检查一次取消状态；结果表使用原子一次性写者声明，分页读取会
循环补齐已发布记录。搜索块至少与模式等长，避免“小块 + 大模式”造成重叠区反复搬移。

搜索结果对比允许从任意已打开文件选择两个搜索会话。对比视图按结果序号分页读取左右
磁盘索引，只构建当前可见的双栏行；同文件和跨文件使用同一条有界内存路径，不复制完整
结果集。每行按源文本内容标记相同、不同、仅左或仅右，并可跳回对应文件的原始命中。

后续正则搜索必须使用同样的分块、取消和磁盘结果契约；多行正则不得隐式读取完整文件。

## 对比策略

块级对比先生成可快速跳转的全局差异概览。I/O 始终使用固定大小缓冲区；当文件过大时，
多个 I/O 块合并为一个概览区域，因此返回区段数量不会随文件大小无限增长。

用户点击候选区段后，只对左右各最多 `1,000` 行的窗口执行精确行级 LCS。矩阵单元格有
硬上限，窗口超限时返回错误并要求缩小范围，禁止对两个百 GB 文件构建完整行序列或
全局编辑图。比较前先把行内容驻留为整数 ID，并裁掉公共前缀和后缀；完全相同窗口只需
`1` 个矩阵单元。损坏 UTF-8 行额外保留原始字节用于精确比较，避免不同坏字节都显示为
替换字符后被误判相同。

## 桌面层

桌面层使用 `egui/eframe`，原因是：

- UI、后台任务和核心均使用 Rust，无需把文本窗口复制到 WebView；
- `ScrollArea::show_rows` 只构建当前可见行；
- 主文本在滚动到窗口边缘时保留锚点并无缝换窗，同时用全文件 `u64` 字节位置提供统一
  滚动概览；界面只显示一个垂直滚动条，用户看到的是一份连续文档，而不是分页；
- 搜索结果将全部命中和各搜索会话标题映射为一个固定行高的虚拟滚动空间，直接按可见行
  从磁盘索引读取，不再额外暴露窗口位置滑杆；
- 正文保留唯一的全文件纵向概览，同时用独立的底部横向拖动条浏览当前窗口中的超宽行；
  搜索结果及其对比视图使用双向虚拟滚动，超宽预览不会被强制压缩或截断；
- 原生文件拖放事件直接复用打开文件流程，可一次打开多个文件；
- 搜索、索引、全文件对比在后台线程运行，可进度报告和取消；
- 只有活动标签启动格式化和结构任务，空闲界面不再固定 5 Hz 重绘；
- 文件位置用全局字节比例与精确 `u64` 输入共同表示，避免把“总行数未知”伪装成已知。

编辑模式保持原文件只读，以原始行字节范围为 Key 保存 UTF-8 替换补丁。补丁内存只随
修改量增长；未修改窗口继续使用 `FileSource` 快速路径。保存使用后台固定缓冲区把原文件
与补丁流式合并到新副本，不允许一次按键整体重写上百 GB 文件，也不原位覆盖源文件。
超长行的窗口片段和损坏的 UTF-8 行不开放直接编辑，避免把不可见原始字节替换掉。

JSON 文件使用独立后台扫描器：固定 `4 MiB` 输入缓冲，按词法状态识别对象 Key、数组下标
和父子层级，不构造完整 `serde_json::Value`。结构索引用紧凑节点数组和共享 UTF-8 Key
字节池；单个 Key 最多保留 256 字节，节点数组与标签池不设固定总量上限，使用
`try_reserve` 按块增长并仅在系统无法继续分配内存时终止。结构树每个同级页面显示
`1,000` 个节点，所有页面均可导航；Key 筛选复用查询缓存、进行无分配 ASCII 大小写匹配，
并以虚拟列表展示全部匹配。

没有换行的 JSON 默认先由后台格式化器生成临时缩进视图。格式化器同样使用固定 `4 MiB`
输入缓冲和流式词法状态，连续字符串和 primitive 批量写出，并限制嵌套深度、输出体积及
扩张倍数。自动格式化不设固定输入大小上限，输出预算按输入大小与最大扩张倍数动态计算；
行索引、搜索、编辑补丁与 JSON 结构随后原子切换到临时视图。存在未保存编辑、保存任务
或搜索任务时禁止切换，所有旧偏移状态会失效。源文件保持只读，只有显式“保存副本”才
输出格式化或编辑后的内容。

XML 使用 `quick-xml` 的流式事件读取器和固定容量缓冲：单行文件在后台写入临时缩进视图，
元素结构索引采用与 JSON 相同的紧凑节点数组和共享名称池。XML 结构树、筛选、面包屑和
跳转只记录元素范围，不构造 DOM；节点跳转同时选中对应正文行，当前位置按节点闭合范围
寻找真正包含偏移的最深节点。XML 结构索引不限制整文件大小、节点总量或名称池总量，
只保留单事件 `16 MiB` 和嵌套 `4,096` 层的解析保护，并通过独立顺序句柄及文件 ID
校验读取打开时的快照。

同扩展名的 JSON/XML 对比先创建后台规范化临时视图，再复用有界块级概览和可见窗口行级
精确对比，仅接受两侧均不超过 `256 MiB` 的输入。JSON 归一化消除字符串外空白；XML
归一化消除排版空白、注释和声明，并稳定属性顺序，但不宣称完整 C14N。普通文本仍走原始
字节对比。普通文本着色和 JSON/XML 语法着色只扫描虚拟列表中的可见行，高亮 span 先按
行号二分定位，单行显示仍受 `32 KiB` 上限保护。

## 验收门槛

在 100 GiB 稀疏文件上：

- 打开过程只读取元数据；
- 能读取开头、任意中间偏移和文件尾；
- 视口分配受配置上限约束；
- 搜索使用固定块缓冲区并可取消；
- 文件在打开后被截断、覆盖或路径替换时，窗口、索引、搜索和对比返回 `SourceChanged`；
- 文件大小不会被转换为 `usize` 后用于整体分配；
- 自动化测试覆盖跨块命中、完整结果落盘、连续向前/向后换窗、行对齐、索引进度、取消
  与显式结果截断 API。

耗时和吞吐量与磁盘、缓存及杀毒软件有关，性能基准必须同时记录硬件和冷热缓存状态。
